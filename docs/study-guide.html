القسم 1

الصورة الكبيرة: شنو يصير لما تدز رسالة؟

أي تطبيق مثل تطبيقنا يتكون من 3 أجزاء:

الجزءشنو هو🍽️ بالمطعم
Frontend (فرونت اند)اللي تشوفه وتضغط عليه: الصفحات والأزرارالصالة والمنيو
Backend (باك اند)السيرفر اللي يشتغل ورا الكواليس ويعالج الطلباتالمطبخ
Database (داتابيس)المكان اللي تنحفظ بيه البيانات بشكل دائمالثلاجة

ورحلة أي طلب تمشي هيچ:

Frontend → Request → API → Backend → Database → Response → Frontend

مثال: علي يدز "هلو" لسارة

  1. علي يكتب "هلو" ويضغط إرسال (Frontend).
  2. الفرونت اند يدز Request للسيرفر، والرسالة بداخله بصيغة JSON.
  3. الـ API يستلم الطلب، والـ Backend يتأكد أن علي مسجل دخول.
  4. الباك اند يحفظ الرسالة بالـ Database باستخدام SQL.
  5. الباك اند يرجع Response يگول "انحفظت".
  6. بنفس اللحظة، الرسالة توصل لسارة عن طريق WebSocket بدون ما تسوي Refresh.

✍️ أسئلة

1. شنو الأجزاء الثلاثة لأي تطبيق مثل تطبيقنا؟
Frontend (الواجهة) و Backend (السيرفر) و Database (مكان حفظ البيانات).
2. وين تنحفظ الرسالة حتى تبقى بعد الـ Refresh؟
بالـ Database.

3. أي جزء "يشوفه" المستخدم ويضغط عليه؟

الـ Frontend هو الواجهة. الباك اند والداتابيس يشتغلون ورا الكواليس.

  • المكتبة (Library): أداة أصغر تسوي شغلة وحدة معينة.

Node.js و npm

JavaScript بالأصل تشتغل داخل المتصفح بس. Node.js مو لغة، هو برنامج يخلي JavaScript تشتغل على جهازك برة المتصفح. نحتاجه حتى نشغّل Next.js.

npm يجي ويا Node.js، وهو مثل متجر تنزل منه المكتبات. من نكتب npm install ينزل كل اللي يحتاجه الفرونت اند.

Tailwind و Responsive

Tailwind CSS طريقة سريعة تكتب بيها التصميم. تحط كلمات جاهزة على العنصر، مثلاً bg-emerald-600 = خلفية خضرة، و rounded-full = زوايا مدورة.

Responsive Design (تصميم متجاوب) معناها الصفحة تتغير حسب حجم الشاشة. بتطبيقنا: على الكمبيوتر القائمة والمحادثة جنب بعض، وعلى الموبايل كل وحدة بشاشة.

"الباك اند بـ Python و Django، والـ API بـ Django REST Framework، والرسائل الفورية بـ Django Channels. الفرونت اند بـ Next.js و TypeScript، والتصميم بـ Tailwind."

✍️ أسئلة

1. Django شنو هو؟

Python هي اللغة، و Django إطار (أدوات جاهزة) مكتوب بيها.

2. ليش نحتاج Node.js بمشروعنا؟

Next.js مكتوب بـ JavaScript، و Node.js هو اللي يشغّل JavaScript على الجهاز.
3. شنو يعني Responsive؟ وشلون تبين بتطبيقنا؟
الصفحة تتغير حسب حجم الشاشة. على الكمبيوتر القائمة والمحادثة جنب بعض، وعلى الموبايل كل وحدة تاخذ الشاشة كلها ويطلع زر رجوع.
4. شنو فايدة Django Channels؟
يخلي Django يدعم WebSocket، حتى الرسائل توصل فوراً بدون Refresh.
القسم 3

JSON

المشكلة: الباك اند مكتوب بـ Python، والفرونت اند بـ JavaScript. شلون يتفاهمون؟ يستخدمون صيغة مشتركة يفهمها الاثنين، وهي JSON.

JSON مو لغة برمجة. هو صيغة بيانات، يعني طريقة متفق عليها حتى نكتب البيانات. شكله بسيط: اسم ← قيمة.

{
  "id": 7,
  "sender": "ali",
  "content": "هلو سارة",
  "is_read": false
}
🍽️ JSON هو ورقة الطلب بالمطعم. الصالة تكتب الطلب بشكل معروف، والمطبخ يقراه ويرجع الجواب بنفس نوع الورقة.

أنواع القيم بـ JSON

النوعمثال
نص (string)"ali"
رقم (number)7
صح/غلط (boolean)true / false
قائمة (array)[1, 2, 3]
كائن (object){"id": 1}
فارغnull
"JSON صيغة بيانات يتفاهم بيها الفرونت اند والباك اند، حتى لو كل واحد مكتوب بلغة مختلفة."

✍️ أسئلة

1. JSON شنو هو؟

JSON صيغة (شكل) لكتابة البيانات، مو لغة برمجة.
2. ليش ما يدز الباك اند البيانات بشكل Python مباشرة؟
لأن الفرونت اند مكتوب بـ JavaScript وما يفهم Python. JSON صيغة مشتركة يفهمها الاثنين.
3. بالمثال فوك، شنو نوع قيمة is_read؟
boolean (صح/غلط)، وقيمتها false يعني الرسالة بعدها ما انقرت.
4. اكتب JSON لمستخدم اسمه sara ورقمه 2 وهو متصل.
{"id": 2, "username": "sara", "is_online": true}
القسم 4

HTTP و Request / Response

HTTP هو الطريق اللي يتراسل بيه المتصفح ويا السيرفر. وكل مرة يصير تواصل، يصير شغلتين:

  1. Request (طلب): الفرونت اند يدز للباك اند.
  2. Response (رد): الباك اند يرجع الجواب.
🍽️ الزبون يگول للنادل "أريد تكة" = Request. النادل يرجع ومعاه الصحن = Response.

الـ Request يتكون من 4 أجزاء

POST /api/conversations/5/messages/
Authorization: Token abc123
{"content": "هلو"}
الجزءبالمثالمعناه
MethodPOSTشنو تريد تسوي (هنا: تضيف)
URL/api/conversations/5/messages/وين (رسائل المحادثة رقم 5)
HeaderAuthorization: Token abc123معلومات إضافية، مثل هويتك
Body{"content": "هلو"}البيانات نفسها بصيغة JSON

الـ Response يتكون من

201 Created
{"id": 7, "content": "هلو", "sender": "ali"}
  • رقم الحالة (Status code): هنا 201 يعني "انخلق بنجاح".
  • Body: الجواب بصيغة JSON.
"الفرونت اند يدز Request بـ HTTP. الطلب بيه Method يحدد شنو نسوي، و URL يحدد وين، و Header بيه الـ Token، و Body بيه البيانات بصيغة JSON. الباك اند يرجع Response بيه رقم حالة وبيانات JSON."

✍️ أسئلة

1. شنو الأجزاء الأربعة للـ Request؟
Method و URL و Header و Body.

2. وين تنحط البيانات (مثل نص الرسالة) بالـ Request؟

البيانات نفسها تروح بالـ Body بصيغة JSON. الـ Header لمعلومات إضافية مثل الـ Token.

3. وين ينحط الـ Token مال تسجيل الدخول؟

ينحط بالـ Header: Authorization: Token ...
4. شنو الفرق بين Request و Response؟
Request هو الطلب اللي يطلع من الفرونت اند للباك اند. Response هو الرد اللي يرجع من الباك اند للفرونت اند.
القسم 5

أرقام الحالة (Status Codes)

كل Response يجي وياه رقم يگول شنو صار. ما تحتاج تحفظهن كلهن، بس هذني المهمات:

الرقمالمعنىمثال من تطبيقنا
200تمامجبت قائمة المستخدمين
201انخلق شي جديدانحفظت رسالة جديدة أو حساب جديد
400إنت دازز بيانات غلطدزيت رسالة فارغة
401ما مسجل دخولطلبت المستخدمين بدون Token
404مو موجودحاولت تقرا محادثة مو إلك
500خطأ بالسيرفر نفسهبق (bug) بالكود

📌 حيلة: اللي يبدي بـ 2 نجاح. بـ 4 الغلط منك (الطلب). بـ 5 الغلط من السيرفر.

✍️ أسئلة

1. علي مو مسجل دخول وطلب قائمة المستخدمين. شنو الرقم؟

401 = ما مسجل دخول.

2. علي دز رسالة وانحفظت. شنو الرقم؟

201 لأن انخلق شي جديد (رسالة جديدة).

3. عمر حاول يقرا محادثة علي وسارة. شنو يرجعله تطبيقنا؟

تطبيقنا يرجع 404 حتى ما يكشف حتى وجود المحادثة لشخص مو مشارك بيها.
4. الأرقام اللي تبدي بـ 5، الغلط من منو؟
من السيرفر (الباك اند)، مو من المستخدم.
القسم 6

Methods و CRUD

الـ Method يگول للباك اند شنو تريد تسوي. وهي 4 رئيسية:

Methodمعناه🍽️ بالمطعم
GETجيب بيانات"جيبلي المنيو"
POSTضيف شي جديد"أريد أطلب طلب جديد"
PATCH / PUTعدّل شي موجود"غيّر الطلب، بلا بصل"
DELETEاحذف"ألغِ الطلب"

CRUD: حيلة الحفظ

  • Create (إضافة) ← POST
  • Read (قراءة) ← GET
  • Update (تعديل) ← PATCH
  • Delete (حذف) ← DELETE

الفرق بين PATCH و PUT: الـ PATCH يعدّل جزء (مثلاً بس is_read). الـ PUT يبدل الشي كله.

بتطبيقنا

لما إنت...الـ Request
تشوف قائمة المستخدمينGET /api/users/
تشوف الرسائل القديمةGET /api/conversations/5/messages/
تسجّل حساب جديدPOST /api/auth/register/
تفتح محادثة ويا شخصPOST /api/conversations/
تقرا الرسائل فتصير ✓✓ زرقةPATCH /api/conversations/5/read/

⚠️ تطبيقنا هسه ما بيه DELETE. هذا ممكن يكون أول شي تكتبه إنت بإيدك.

✍️ أسئلة

1. سارة تريد تشوف محادثاتها. أي Method؟

تشوف بس = قراءة = GET.

2. علي يريد يصحح غلطة إملائية برسالة دازها. أي Method؟

تعديل شي موجود = PATCH.

3. مستخدم جديد يسجّل حساب. أي Method؟

إضافة شي جديد (حساب) = POST.
4. شنو الفرق بين PATCH و PUT؟
PATCH يعدّل جزء من الشي. PUT يبدل الشي كله.
5. شنو يعني CRUD؟
Create و Read و Update و Delete، يعني إضافة وقراءة وتعديل وحذف. وتقابلها POST و GET و PATCH و DELETE.
القسم 7

API و Token

API هي مجموعة "أبواب" (روابط) يفتحها الباك اند حتى الفرونت اند يطلب منها. كل باب اله رابط ووظيفة. مثلاً /api/users/ باب لقائمة المستخدمين.

🍽️ الـ API هو المنيو. يگولك شنو تكدر تطلب وشلون تطلبه. ما تحتاج تعرف شلون المطبخ يطبخ.

كل روابط تطبيقنا

Methodالرابطالوظيفة
POST/api/auth/register/تسجيل، يرجع Token
POST/api/auth/login/دخول، يرجع Token
GET/api/auth/me/معلوماتي
GET/api/users/قائمة المستخدمين
GET/api/conversations/محادثاتي
POST/api/conversations/فتح محادثة
GET/api/conversations/5/messages/الرسائل السابقة
POST/api/conversations/5/messages/إرسال رسالة
PATCH/api/conversations/5/read/تعليم كمقروء

الـ Token: شلون السيرفر يعرف منو إنت؟

  1. تسجّل دخول بالاسم والباسورد.
  2. السيرفر يتأكد ويرجعلك Token، وهو نص سري طويل مثل abc123....
  3. الفرونت اند يحفظه بالمتصفح (localStorage).
  4. بكل Request بعدين، يحطه بالـ Header: Authorization: Token abc123.
  5. السيرفر يشوف الـ Token ويعرف إنت منو.
🎫 الـ Token مثل باج الدخول بالشركة. تاخذه مرة وحدة بالاستقبال، وبعدين كل باب تفتحه بيه بدون ما تعرّف نفسك من جديد.

الباسورد

ما نحفظ الباسورد نص عادي أبداً. Django يشفّره (hash)، يعني يحوله لنص مخربط ما يرجع. إذا أحد سرق الداتابيس، ما يكدر يعرف الباسوردات.

✍️ أسئلة

1. شنو هو الـ API؟
مجموعة روابط (أبواب) يفتحها الباك اند حتى الفرونت اند يطلب منها بيانات أو يسوي عمليات.
2. شنو يصير لو نسينا نحط الـ Token بالـ Header؟
السيرفر ما يعرف منو إنت، ويرجع 401.
3. ليش ما نحفظ الباسورد نص عادي؟
حتى لو أحد سرق الداتابيس ما يعرف الباسوردات. نحفظه مشفّر (hash).

4. وين يحفظ الفرونت اند الـ Token بتطبيقنا؟

يحفظه بـ localStorage حتى يبقى بعد الـ Refresh.
القسم 8

Database (الداتابيس)

الداتابيس هي المكان اللي تنحفظ بيه البيانات بشكل دائم. إذا السيرفر انطفى أو سويت Refresh، الرسائل تبقى.

🍽️ الداتابيس هي الثلاجة. الأغراض تبقى بيها حتى لو المطبخ سكّر وفتح.

شكلها من جوة: جداول

idsendercontentis_read
1aliهلو سارة✅
2saraهلا علي❌
  • Table (جدول): مجموعة بيانات من نفس النوع. هذا جدول الرسائل.
  • Column (عمود) ⬇️: نوع المعلومة. مثلاً عمود content بيه نصوص كل الرسائل.
  • Row (صف) ➡️: سجل واحد كامل. مثلاً الصف 2 = رسالة سارة "هلا علي".

جداول تطبيقنا

الجدولشنو يحفظأهم الأعمدة
usersالمستخدمينid, username, password (مشفّر)
profileالحالةuser_id, is_online, last_seen
conversationsالمحادثاتid, created_at
messagesالرسائلid, conversation_id, sender_id, content, created_at, is_read

نستخدم هسه SQLite (داتابيس بملف واحد، ممتازة للتجربة). بالإنتاج نحولها لـ PostgreSQL.

"كل رسالة هي صف، وكل معلومة عن الرسالة (المرسل، النص، مقروءة لو لا) هي عمود."

✍️ أسئلة

1. ليش نحتاج داتابيس؟
حتى البيانات (الرسائل، المستخدمين) تبقى محفوظة بشكل دائم، حتى لو السيرفر انطفى أو سويت Refresh.
2. بجدول الرسائل فوك، شكد عدد الصفوف وشكد عدد الأعمدة؟
صفّين (رسالتين) و 4 أعمدة (id, sender, content, is_read).

3. رسالة وحدة كاملة بالجدول، شنو تسمى؟

كل رسالة = صف. العمود هو نوع المعلومة.
4. شنو الداتابيس اللي نستخدمها هسه، وشنو نستخدم بالإنتاج؟
هسه SQLite، وبالإنتاج PostgreSQL.
القسم 9

SQL

SQL هي اللغة اللي نحچي بيها ويا الداتابيس: نجيب ونضيف ونعدل ونحذف.

🍽️ الثلاجة ما تفتح وحدها. SQL هي الإيد اللي تفتحها وتاخذ منها أو تحط بيها.

الأوامر الأربعة (نفس CRUD)

الـ Method (API)أمر SQLالشغل
GETSELECTجيب
POSTINSERTضيف
PATCHUPDATEعدّل
DELETEDELETEاحذف

أمثلة من تطبيقنا

سارة تفتح المحادثة وتشوف الرسائل:

SELECT * FROM messages WHERE conversation_id = 5 ORDER BY created_at;

📖 تنقرا: "جيب كل (*) الرسائل من جدول messages وين المحادثة رقم 5، مرتبة حسب الوقت".

علي يدز رسالة:

INSERT INTO messages (conversation_id, sender_id, content) VALUES (5, 1, 'hello');

سارة قرت الرسائل:

UPDATE messages SET is_read = true WHERE conversation_id = 5 AND sender_id = 1;

حذف رسالة:

DELETE FROM messages WHERE id = 7;

⚠️ انتبه: UPDATE و DELETE بدون WHERE يأثرن على كل الصفوف! يعني DELETE FROM messages; يمسح كل الرسائل.

📌 حيلة SELECT لو INSERT؟

اسأل نفسك: "هل انضاف شي جديد للداتابيس؟" لا، بس أشوف ← SELECT. إي، انضاف ← INSERT.

ORM: Django يكتب SQL بدالنا

بالكود مالتنا ما كتبنا SQL بإيدنا. Django عنده ORM يحول كود Python لـ SQL تلقائياً:

Python (Django ORM)SQL اللي يتنفذ
Message.objects.create(...)INSERT
conv.messages.all()SELECT
.update(is_read=True)UPDATE
message.delete()DELETE
"استخدمت Django ORM، وهو يحول كود Python لـ SQL. مثلاً Message.objects.create يتحول لـ INSERT. بس أفهم الـ SQL اللي يصير ورا الكواليس."

✍️ أسئلة

1. سارة فتحت المحادثة تشوف الرسائل القديمة. أي أمر؟

تشوف بس، ما انضاف شي = SELECT.

2. سارة حذفت رسالة. أي أمر؟

حذف = DELETE.

3. الرسالة صارت مقروءة ✓✓. أي أمر؟

عدلنا قيمة is_read برسالة موجودة = UPDATE.
4. شنو يسوي هذا الأمر؟ SELECT * FROM users;
يجيب كل الأعمدة لكل المستخدمين من جدول users.
5. اكتب أمر SQL يجيب رسائل علي بس (sender_id = 1).
SELECT * FROM messages WHERE sender_id = 1;
6. ليش DELETE بدون WHERE خطر؟
لأن يحذف كل الصفوف بالجدول، مو صف واحد.
7. شنو هو الـ ORM؟

القسم 10

Primary Key و Foreign Key

🔑 Primary Key (المفتاح الأساسي)

رقم مميز لكل صف، ما يتكرر أبداً. بتطبيقنا هو عمود id.

id 🔑sendercontent
1aliهلو
2saraهلو

نفس النص "هلو"، بس كل رسالة إلها رقم خاص بيها.

🪪 مثل الرقم الوطني: اسمين ممكن يتشابهون، بس الرقم ما يتكرر.

🔗 Foreign Key (المفتاح الأجنبي)

عمود بجدول يأشر على Primary Key بجدول ثاني. وظيفته يربط الجداول.

جدول users:

id 🔑username
1ali
2sara

جدول messages:

id 🔑sender_id 🔗conversation_id 🔗content
115هلو سارة
225هلا علي

sender_id = 1 معناه "روح لجدول users وشوف منو رقمه 1" ← ali.

ليش ما نكتب الاسم مباشرة؟ لأن إذا علي غيّر اسمه، نغيره بمكان واحد بس، وكل رسائله تبقى مربوطة بيه صح.

أنواع العلاقات

العلاقةمعناهابتطبيقنا
One-to-Oneواحد ← واحدكل مستخدم إله Profile واحد
One-to-Many (ForeignKey)واحد ← هوايةالمحادثة الوحدة بيها هواية رسائل
Many-to-Manyهواية ← هوايةالمستخدم بهواية محادثات، والمحادثة بيها أكثر من مستخدم

CASCADE: إذا انحذفت محادثة، رسائلها تنحذف وياها تلقائياً (on_delete=CASCADE).

"Primary Key رقم مميز لكل صف. Foreign Key عمود يربط جدول بجدول ثاني، مثل sender_id بجدول الرسائل يأشر على المستخدم اللي دزها."

✍️ أسئلة

1. عمود conversation_id بجدول الرسائل شنو هو؟

Foreign Key، لأنه يأشر على الـ id (Primary Key) بجدول المحادثات، يعني يربط الرسالة بمحادثتها.

2. عمود id بجدول الرسائل شنو هو؟

Primary Key، رقم مميز لكل رسالة.
3. ليش نخزن sender_id بدل اسم المرسل؟
حتى إذا المستخدم غيّر اسمه نغيره بمكان واحد، والربط يبقى صحيح. وأيضاً الرقم ما يتكرر بس الاسم ممكن يتشابه.
4. العلاقة بين المحادثة والرسائل شنو نوعها؟
One-to-Many: محادثة وحدة بيها هواية رسائل.
5. شنو يصير لرسائل محادثة إذا انحذفت المحادثة؟
تنحذف وياها، بسبب on_delete=CASCADE.
القسم 11

WebSocket: ليش الرسالة توصل فوراً؟

المشكلة ويا HTTP

بـ HTTP، الفرونت اند لازم يطلب أول حتى ياخذ جواب. السيرفر ما يكدر يبدي يحچي وحده.

يعني علي دز رسالة، بس سارة ما تعرف إلا إذا سوت Refresh. الحل الغبي: سارة تسأل السيرفر كل ثانية "اكو رسالة جديدة؟" وهذا اسمه Polling، وهو هدر لأن أغلب الأجوبة "لا".

📬 HTTP مثل تروح لصندوق البريد كل شوية تشوف إذا اكو رسالة.
📞 WebSocket مثل مكالمة تلفون مفتوحة: أي واحد يحچي بأي وقت والثاني يسمع فوراً.

شنو هو WebSocket؟

اتصال يبقى مفتوح بين المتصفح والسيرفر، وبالاتجاهين. السيرفر يكدر يدز رسالة لسارة لحظة ما توصل من علي، بدون ما سارة تطلب.

HTTPWebSocket
الاتصالينفتح وينسد بكل طلبيبقى مفتوح
منو يبدي؟الفرونت اند بسالاثنين
بتطبيقنا نستخدمه لـالبيانات القديمة: القوائم والرسائل السابقة والتسجيلالأحداث الحية: رسالة جديدة، يكتب...، متصل، مقروء
الرابط يبدي بـhttp://ws://

بتطبيقنا

ws://localhost:8000/ws/chat/5/?token=abc123

ليش الـ Token بالرابط مو بالـ Header؟ لأن المتصفح ما يسمح تضيف Header لاتصال WebSocket.

الرسائل اللي تنتقل بالـ WebSocket هم هم JSON:

الفرونت اند يدز:

{"type": "message", "content": "hello"}

السيرفر يدز لكل اللي بالمحادثة:

{"type": "message", "message": {"id": 7, "content": "hello", ...}}

وأحداث ثانية (يكتب، متصل، مقروء):

{"type": "typing", "user_id": 1}
{"type": "presence", "user_id": 1, "is_online": true}
{"type": "read", "reader_id": 2}
"استخدمت WebSocket لأن الشات يحتاج السيرفر يدز الرسالة للطرف الثاني لحظة وصولها. بـ HTTP لازم الطرف الثاني يسأل كل شوية (Polling) وهذا هدر. الـ WebSocket اتصال يبقى مفتوح وبالاتجاهين."

✍️ أسئلة

1. ليش ما نكتفي بـ HTTP للشات؟
لأن بـ HTTP السيرفر ما يكدر يدز شي إلا إذا الفرونت اند طلب. فسارة ما تعرف بالرسالة الجديدة إلا بـ Refresh أو Polling.
2. شنو هو Polling وليش سيء؟
الفرونت اند يسأل السيرفر كل شوية "اكو جديد؟". سيء لأن أغلب الطلبات جوابها "لا"، فهو هدر للسيرفر والإنترنت والبطارية.

3. عرض الرسائل القديمة لما تفتح محادثة، يصير بـ؟

البيانات القديمة نجيبها بـ HTTP GET. الـ WebSocket للأحداث الجديدة الحية.

4. "سارة يكتب..." توصل لعلي بـ؟

حدث حي ولحظي = WebSocket.
5. ليش نحط الـ Token بالرابط بالـ WebSocket؟
لأن المتصفح ما يسمح نضيف Header لاتصال WebSocket.
القسم 12

Channels: شلون الرسالة توصل للشخص الصح؟

Django Channels هي المكتبة اللي تخلي Django يفهم WebSocket. بيها 3 أفكار مهمة:

1. Consumer

مثل الـ View بس للـ WebSocket. الـ View يستلم Request واحد ويرجع Response وينتهي. الـ Consumer يبقى شغال طول ما الاتصال مفتوح. بيه 3 دوال:

  • connect(): لما أحد يفتح اتصال. نتأكد من الـ Token وأنه مشارك بالمحادثة.
  • receive_json(): لما توصل رسالة. نحفظها بالداتابيس ونبثها.
  • disconnect(): لما الاتصال ينسد.

2. Group (غرفة)

مجموعة اتصالات نكدر ندزلها كلها سوه. كل من فاتح المحادثة 5 ينضم لغرفة chat_5. من علي يدز رسالة، نبثها لكل الغرفة، فتوصل لسارة.

🏠 الـ Group مثل كروب واتساب: تدز بيه مرة وحدة ويوصل لكل الأعضاء.

بتطبيقنا 3 أنواع غرف:

الغرفةمنو بيهاشنو ينبث بيها
chat_5كل من فاتح المحادثة 5الرسائل، يكتب...، مقروء
presenceكل المستخدمين المتصلينفلان صار متصل / غير متصل
user_2سارة بستنبيه "وصلتك رسالة" حتى لو المحادثة مو مفتوحة، حتى تتحدث قائمتها

3. Channel Layer (البريد)

النظام اللي يوصل الرسائل بين الاتصالات والغرف. هسه نستخدم InMemory (بذاكرة السيرفر، يكفي للتجربة). بالإنتاج ويا أكثر من سيرفر نستخدم Redis.

الرحلة الكاملة لرسالة بالـ WebSocket

Ali browser → WebSocket → ChatConsumer.receive_json → INSERT (Database) → group_send("chat_5") → Sara browser
"استخدمت Django Channels. كل محادثة إلها Group، ومن توصل رسالة الـ Consumer يحفظها بالداتابيس ويبثها للـ Group فتوصل لكل المشاركين. الـ Channel layer هسه InMemory، وبالإنتاج Redis."

✍️ أسئلة

1. شنو الفرق بين View و Consumer؟
الـ View يستلم Request واحد ويرجع Response وينتهي (HTTP). الـ Consumer يبقى شغال طول ما اتصال الـ WebSocket مفتوح ويكدر يستلم ويدز بأي وقت.
2. شنو هو الـ Group؟
غرفة بيها مجموعة اتصالات، ندز لها مرة وحدة ويوصل للكل. مثل كروب واتساب.

3. إذا صار عدنا 3 سيرفرات، شنو نغير؟

InMemory يعيش بذاكرة سيرفر واحد. ويا أكثر من سيرفر نحتاج Redis حتى يتشاركون. ونحول الداتابيس لـ PostgreSQL.
4. ليش سوينا غرفة user_2 لسارة؟
حتى توصلها تنبيهات الرسائل الجديدة حتى لو المحادثة مو مفتوحة عندها، فتتحدث قائمة المحادثات وعدد غير المقروء بدون Refresh.
5. بأي دالة بالـ Consumer نتأكد من الـ Token؟
بـ connect().

🐳 شنو هو Docker؟

Docker برنامج يشغّل التطبيقات داخل صناديق مسدودة (Containers). كل صندوق بيه تطبيق كامل ويا كل اللي يحتاجه (Python، مكتبات، إعدادات).

الصندوق يكدر يربط باب من داخله بباب بجهازك. مثلاً 0.0.0.0:8000->8000/tcp معناها: أي طلب يوصل لباب 8000 بجهازك، يروح لباب 8000 داخل الصندوق.

📦 Docker مثل شقق مفروشة جاهزة: تسكن بيها فوراً بدون ما تشتري أثاث. بس إذا نسيت شقة مسكونة، تبقى شاغلة رقمها بالعمارة!
الأمرشنو يسوي
docker psيطلع الصناديق الشغالة
docker stop <name>يوكف صندوق (ما يمسحه)
docker start <name>يرجع يشغله

🚪 شنو هو daphne؟

كود Django اللي كتبناه (views و models) ما يعرف يستقبل طلبات من الشبكة وحده. يعرف بس "إذا وصلني Request شنو أسوي". فنحتاج برنامج يوكف على الباب (البورت)، يستلم الطلبات، يسلمها لـ Django، ويرجع الجواب. هذا اسمه سيرفر (Server)، و daphne واحد منهم.

🍽️ Django = الطباخ، يعرف يطبخ بس ما يوكف على الباب. daphne = النادل على الباب، يستقبل الطلبات ويوصلها للطباخ ويرجع الصحون. البورت 8000 = رقم باب المطعم.

ليش daphne بالذات؟

النوعيدعمأمثلة
WSGI (القديم)HTTP بسgunicorn، runserver القديم
ASGI (الجديد)HTTP و WebSocketdaphne، uvicorn

تطبيقنا يحتاج WebSocket، فلازم سيرفر ASGI. و daphne سوّاه نفس فريق Django Channels.

نفكك الأمر

daphne -p 8000 config.asgi:application
الجزءمعناه
daphneشغّل السيرفر
-p 8000اوكف على باب (port) رقم 8000
config.asgiروح لملف backend/config/asgi.py
:applicationوخذ منه المتغير application

و application بملف asgi.py يگرر: إذا الطلب HTTP يوديه لـ Django (الـ API)، وإذا WebSocket يوديه لـ Channels (الشات المباشر).

❓ هل daphne هو الـ API؟ لا!

  • الـ API = المنيو: قائمة الروابط اللي تطبيقنا يقبلها وشنو يسوي كل واحد. إحنا كتبناه: الروابط بـ urls.py، والمنطق بـ views.py.
  • daphne = النادل: يوصّل أي طلب للكود مالتنا. ما يعرف شنو يعني /api/users/، بس يوصله.

رحلة طلب GET /api/users/:

Browser → daphne (port 8000) → config/asgi.py → urls.py → views.py → Database → views.py → daphne → Browser

الـ API يبدي من urls.py: هناك يتقرر هذا الرابط يروح لأي view.

🧪 الدليل من اللي صار: مشروع hum هم يستخدم daphne، ومشروعنا هم daphne. بس كل واحد إله API مختلف. لهذا لما طلبنا من باب 8000 رد علينا API مال hum، وما عرفنا.

"الـ API هو الروابط اللي عرّفتها بـ urls.py ومنطقها بـ views.py. و daphne سيرفر ASGI يستقبل طلبات HTTP و WebSocket على البورت ويسلمها لـ Django. استخدمته بدل runserver لأن تطبيقي يحتاج WebSocket عن طريق Django Channels."

🌐 شنو هو CORS؟

CORS قاعدة أمان بالمتصفح: الموقع ما يكدر يحچي ويا سيرفر ثاني إلا إذا السيرفر وافق. السيرفر عنده قائمة بالمواقع المسموحة.

المتصفح قبل الطلب الحقيقي يدز طلب استئذان اسمه preflight (نوعه OPTIONS). إذا السيرفر ما رد بـ "مسموح" (Header اسمه Access-Control-Allow-Origin)، المتصفح يوكف الطلب ويطلع "Failed to fetch".

🍽️ المطعم يستقبل طلبات بس من صالته. إذا أحد دز طلب من صالة ثانية، النادل يرفضه. CORS يحمي المستخدم: موقع غريب ما يكدر يستخدم حسابك بموقع ثاني.
"CORS قاعدة أمان بالمتصفح. السيرفر لازم يوافق على الموقع اللي يطلب منه. بمشروعي بالتطوير سمحت لأي بورت على localhost، وبالإنتاج أحدد الموقع الحقيقي بس."

🧠 شلون يفكر المبرمج (أهم درس)

  1. شوف الخطأ: مثل "Failed to fetch". هذا وحده ما يگول السبب.
  2. اجمع معلومات أكثر: الـ Console (F12)، الـ Terminal، الأوامر اللي تفحص.
  3. افهم السبب: مثلاً "الباب غلط" أو "البرنامج القديم بعده شغال".
  4. صلّح شي واحد بس، وجرب مرة ثانية.

📌 القاعدة الذهبية: لا تخمّن، اجمع معلومات أول. واكتب الأوامر كل سطر وحده حتى تعرف أي واحد فشل.

✍️ أسئلة

1. "Address already in use" معناها؟

كل بورت يسكنه برنامج واحد. اكو برنامج قديم شاغل نفس البورت.

2. شافوا "Failed to fetch". شنو أول خطوة؟

لا تخمّن، اجمع معلومات أول.

3. ليش نستخدم venv (بيئة افتراضية)؟

كل مشروع إله صندوقه، والنظام يبقى سليم.
4. ليش صار الفرونت اند على 3001 بدل 3000؟
لأن 3000 جان محجوز ببرنامج ثاني (نسخة ثانية من الفرونت اند)، فـ Next.js ينتقل للبورت اللي بعده.
5. شنو هو CORS بجملة وحدة؟
قاعدة أمان بالمتصفح: الموقع ما يكدر يطلب من سيرفر ثاني إلا إذا السيرفر وافق على هذا الموقع.
6. طلعلك "No module named 'config'". شنو أول شي تشيك عليه؟
إنت بأي فولدر. لازم تكون داخل ~/chat/backend لما تشغل daphne.
7. شنو يسوي fuser -k 8000/tcp؟
يطفي أي برنامج شاغل البورت 8000.
8. ليش سحب التصليح (git pull) ما كفى وحده؟
لأن الـ daphne القديم بعده شغال بالكود القديم. لازم نطفيه ونشغله من جديد حتى ياخذ التصليح.

9. هل daphne هو الـ API؟

daphne = النادل، والـ API = المنيو اللي كتبناه.

10. ليش استخدمنا daphne (ASGI) مو سيرفر WSGI؟

WSGI يدعم HTTP بس، و ASGI يدعم HTTP و WebSocket.
11. شنو الفرق بين docker stop ومسح المشروع؟
docker stop يوكف الصندوق بس، والمشروع يبقى موجود. ترجعه بـ docker start.
12. ss -ltnp طلع البورت محجوز بس بدون اسم برنامج. شنو تسوي؟
تستخدم sudo ss -ltnp حتى يطلع الاسم، لأن البرنامج مال مستخدم ثاني. وإذا طلع docker-proxy تستخدم docker ps.
13. وضح بجملة: شنو يسوي daphne -p 8000 config.asgi:application؟
يشغل سيرفر daphne على باب 8000، وياخذ التطبيق من المتغير application بملف config/asgi.py.
