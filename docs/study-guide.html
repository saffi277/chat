1الصورة الكبيرة: ماذا يحدث حين ترسل رسالة؟

أي تطبيق مثل تطبيقنا يتكوّن من ثلاثة أجزاء:

الجزءما هو🍽️ في المطعم
Frontend (الواجهة)ما تراه وتضغط عليه: الصفحات والأزرارالصالة وقائمة الطعام
Backend (الخادم)البرنامج الذي يعمل خلف الكواليس ويعالج الطلباتالمطبخ
Database (قاعدة البيانات)المكان الذي تُحفظ فيه البيانات حفظاً دائماًالثلاجة

ورحلة أي طلب تسير هكذا:

Frontend → Request → API → Backend → Database → Response → Frontend

مثال: عليّ يرسل «مرحباً» إلى سارة

  1. يكتب علي «مرحباً» ويضغط إرسال (Frontend).
  2. ترسل الواجهة طلباً (Request) إلى الخادم، والرسالة داخله بصيغة JSON.
  3. يستقبل الـ API الطلب، ويتأكد الخادم أن علياً مسجّل الدخول.
  4. يحفظ الخادم الرسالة في قاعدة البيانات مشفّرة، باستعمال SQL.
  5. يعيد الخادم رداً (Response) يقول «حُفظت».
  6. وفي اللحظة نفسها تصل الرسالة إلى سارة عبر WebSocket دون أن تحدّث الصفحة.

✍️ أسئلة

1. ما الأجزاء الثلاثة لأي تطبيق مثل تطبيقنا؟
الواجهة (Frontend)، والخادم (Backend)، وقاعدة البيانات (Database).
2. أين تُحفظ الرسالة لتبقى بعد تحديث الصفحة؟
في قاعدة البيانات.

3. أي جزء يراه المستخدم ويضغط عليه؟

الواجهة هي ما يراه المستخدم، والخادم وقاعدة البيانات يعملان خلف الكواليس.

2اللغة، وإطار العمل، والمكتبة

ثلاث كلمات تتكرر كثيراً، ويجب التفريق بينها:

  • لغة البرمجة: الكلمات والقواعد التي نكتب بها الكود، مثل Python وJavaScript وTypeScript.
  • إطار العمل (Framework): هيكل جاهز مكتوب بلغة معيّنة، يعطيك الأدوات الأساسية فلا تبدأ من الصفر، مثل Django وNext.js. الإطار ليس لغة؛ أنت تكتب داخله بلغته.
  • المكتبة (Library): أداة أصغر تؤدي مهمة واحدة معيّنة، مثل Pillow لفحص الصور.
🧱 اللغة هي الطوب والإسمنت، وإطار العمل هو الهيكل الخرساني الجاهز للبناية: تبني داخله، لكن بالطوب نفسه.

لماذا TypeScript؟ وما علاقتها بـ Next.js؟

Next.js إطار، والكود داخله يُكتب بإحدى لغتين فقط: JavaScript أو TypeScript. وTypeScript هي JavaScript نفسها مع إضافة «الأنواع»: تكتب name: string فيكتشف المحرّر الأخطاء قبل التشغيل. وعند البناء تتحول تلقائياً إلى JavaScript، فالمتصفح لا يرى إلا JavaScript. واخترناها لأن Next.js نفسه يقترحها افتراضياً. (وفي القسم 21 طرق التمييز بين اللغات، وفي القسم 23 ما تقوله للمدير.)

Node.js وnpm

كانت JavaScript في الأصل تعمل داخل المتصفح فقط. وNode.js ليس لغة، بل برنامج يشغّل JavaScript على جهازك خارج المتصفح؛ نحتاجه لتشغيل Next.js.

وnpm يأتي مع Node.js، وهو مثل متجر تُنزَّل منه المكتبات. الأمر npm install ينزّل كل ما تحتاجه الواجهة.

Tailwind والتصميم المتجاوب

Tailwind CSS طريقة سريعة لكتابة التصميم: تضع كلمات جاهزة على العنصر، مثل rounded-full (زوايا دائرية) وflex (ترتيب العناصر في صف).

والتصميم المتجاوب (Responsive) يعني أن الصفحة تتغير بحسب حجم الشاشة: في الحاسوب القائمة والمحادثة متجاورتان، وفي الهاتف كل منهما تأخذ الشاشة كلها.

«الخادم بلغة Python وإطار Django، والـ API بـ Django REST Framework، والرسائل الفورية بـ Django Channels. والواجهة بلغة TypeScript وإطار Next.js مع React، والتصميم بـ Tailwind.»

✍️ أسئلة

1. ما هو Django؟

Python هي اللغة، وDjango إطار (أدوات جاهزة) مكتوب بها.

2. ما هو Next.js؟

Next.js إطار، وليس لغة. لغتنا داخله TypeScript.

3. لماذا نحتاج Node.js في مشروعنا؟

Next.js مكتوب بـ JavaScript، وNode.js هو الذي يشغّل JavaScript على الجهاز.
4. ما معنى Responsive؟ وكيف يظهر في تطبيقنا؟
الصفحة تتغير بحسب حجم الشاشة. في الحاسوب القائمة والمحادثة متجاورتان، وفي الهاتف تأخذ كل واحدة الشاشة كلها ويظهر زر رجوع.
5. ما فائدة Django Channels؟
تجعل Django يدعم WebSocket، فتصل الرسائل فوراً دون تحديث الصفحة.

3JSON

المشكلة: الخادم مكتوب بـ Python، والواجهة بـ TypeScript. فكيف يتفاهمان؟ يستعملان صيغة مشتركة يفهمها الطرفان، وهي JSON.

JSON ليس لغة برمجة، بل صيغة بيانات: طريقة متفق عليها لكتابة البيانات. وشكله بسيط: اسم ← قيمة.

{
  "id": 7,
  "sender": "ali",
  "content": "مرحباً سارة",
  "is_read": false
}
🍽️ JSON هو ورقة الطلب في المطعم: الصالة تكتب الطلب بشكل معروف، والمطبخ يقرؤه ويعيد الجواب بالشكل نفسه.

أنواع القيم في JSON

النوعمثال
نص (string)"ali"
رقم (number)7
صح أو خطأ (boolean)true / false
قائمة (array)[1, 2, 3]
كائن (object){"id": 1}
فارغnull
«JSON صيغة بيانات يتفاهم بها الخادم والواجهة، حتى لو كُتب كل منهما بلغة مختلفة.»

✍️ أسئلة

1. ما هو JSON؟

JSON صيغة (شكل) لكتابة البيانات، وليس لغة برمجة.
2. لماذا لا يرسل الخادم البيانات بصيغة Python مباشرة؟
لأن الواجهة مكتوبة بـ TypeScript ولا تفهم Python، وJSON صيغة مشتركة يفهمها الطرفان.
3. في المثال أعلاه، ما نوع قيمة is_read؟
boolean (صح أو خطأ)، وقيمتها false أي أن الرسالة لم تُقرأ بعد.
4. اكتب JSON لمستخدم اسمه sara ورقمه 2 وهو متصل.
{"id": 2, "username": "sara", "is_online": true}

4HTTP والطلب والرد (Request / Response)

HTTP هو الطريق الذي يتراسل به المتصفح مع الخادم. وفي كل تواصل يحدث أمران:

  1. الطلب (Request): ترسله الواجهة إلى الخادم.
  2. الرد (Response): يعيده الخادم.
🍽️ يقول الزبون للنادل «أريد طبقاً» فهذا طلب، ويعود النادل بالطبق فهذا رد.

الطلب يتكوّن من أربعة أجزاء

POST /api/conversations/5/messages/
Authorization: Token abc123
{"content": "مرحباً"}
الجزءفي المثالمعناه
MethodPOSTماذا تريد أن تفعل (هنا: تضيف)
URL/api/conversations/5/messages/أين (رسائل المحادثة رقم 5)
HeaderAuthorization: Token abc123معلومات إضافية، مثل هويتك
Body{"content": "مرحباً"}البيانات نفسها بصيغة JSON

والرد يتكوّن من

201 Created
{"id": 7, "content": "مرحباً", "sender": {...}}
  • رقم الحالة (Status code): هنا 201، أي «أُنشئ بنجاح».
  • Body: الجواب بصيغة JSON.
«ترسل الواجهة طلب HTTP فيه Method يحدد العملية، وURL يحدد المكان، وHeader فيه التوكن، وBody فيه البيانات بصيغة JSON. ويعيد الخادم رداً فيه رقم حالة وبيانات JSON.»

✍️ أسئلة

1. ما الأجزاء الأربعة للطلب؟
Method وURL وHeader وBody.

2. أين توضع البيانات (مثل نص الرسالة) في الطلب؟

البيانات نفسها في الـ Body بصيغة JSON، والـ Header للمعلومات الإضافية مثل التوكن.

3. أين يوضع توكن الدخول؟

في الـ Header: Authorization: Token ...
4. ما الفرق بين الطلب والرد؟
الطلب يخرج من الواجهة إلى الخادم، والرد يعود من الخادم إلى الواجهة.

5أرقام الحالة (Status Codes)

كل رد يأتي معه رقم يخبرك بما حدث. لا تحتاج إلى حفظها كلها، بل هذه المهمة:

الرقمالمعنىمثال من تطبيقنا
200تم بنجاحجلبتَ قائمة محادثاتك
201أُنشئ شيء جديدحُفظت رسالة جديدة، أو أُنشئ حساب
204تم، ولا محتوى في الردحذفتَ رسالة، أو سجّلتَ الخروج
400البيانات التي أرسلتها خاطئةأرسلتَ رسالة فارغة
401لستَ مسجّل الدخولطلبتَ المحادثات دون توكن
403مسجّل الدخول لكن غير مسموح لكطالب يحاول النشر في قناة
404غير موجودحاولتَ قراءة محادثة لستَ عضواً فيها
429طلبات كثيرة جداً في وقت قصيرتجاوزتَ حد الإرسال في الدقيقة
500خطأ في الخادم نفسهعلّة (bug) في الكود

📌 قاعدة سهلة: ما يبدأ بـ 2 نجاح، وما يبدأ بـ 4 فالخطأ من الطلب، وما يبدأ بـ 5 فالخطأ من الخادم.

✍️ أسئلة

1. علي غير مسجّل الدخول وطلب قائمة محادثاته. ما الرقم؟

401 = لستَ مسجّل الدخول.

2. أرسل علي رسالة فحُفظت. ما الرقم؟

201 لأنه أُنشئ شيء جديد (رسالة جديدة).

3. حاول عمر قراءة محادثة علي وسارة. ماذا يعيد تطبيقنا؟

يعيد 404 حتى لا يكشف وجود المحادثة أصلاً لمن ليس عضواً فيها.
4. الأرقام التي تبدأ بـ 5، الخطأ ممن؟
من الخادم، لا من المستخدم.
5. ما الفرق بين 401 و403؟
401: الخادم لا يعرف من أنت (لا توكن). 403: يعرفك، لكنك لا تملك الصلاحية، مثل طالب يحاول إنشاء قناة.

6الطرق (Methods) وCRUD

الـ Method يخبر الخادم بما تريد أن تفعله، والأربعة الرئيسية:

Methodمعناه🍽️ في المطعم
GETاجلب بيانات«أحضر لي قائمة الطعام»
POSTأضف شيئاً جديداً«أريد طلباً جديداً»
PATCH / PUTعدّل شيئاً موجوداً«غيّر الطلب، بلا بصل»
DELETEاحذف«ألغِ الطلب»

CRUD: طريقة للحفظ

  • Create (إضافة) ← POST
  • Read (قراءة) ← GET
  • Update (تعديل) ← PATCH
  • Delete (حذف) ← DELETE

الفرق بين PATCH وPUT: PATCH يعدّل جزءاً (مثلاً الاسم فقط)، وPUT يستبدل الشيء كله.

أمثلة حقيقية من تطبيقنا

حين تفعل...الطلب

✍️ أسئلة

1. تريد سارة رؤية محادثاتها. أي Method؟

رؤية فقط = قراءة = GET.

2. يريد علي تصحيح خطأ إملائي في رسالة أرسلها. أي Method؟

تعديل شيء موجود = PATCH.

3. مستخدم جديد ينشئ حساباً. أي Method؟

إضافة شيء جديد (حساب) = POST.
4. ما الفرق بين PATCH وPUT؟
PATCH يعدّل جزءاً من الشيء، وPUT يستبدله كله.
5. ما معنى CRUD؟
Create وRead وUpdate وDelete، أي الإضافة والقراءة والتعديل والحذف، ويقابلها POST وGET وPATCH وDELETE.

7الـ API والتوكن

الـ API مجموعة «أبواب» (روابط) يفتحها الخادم لتطلب منها الواجهة. لكل باب رابط ووظيفة؛ مثلاً /api/conversations/ باب قائمة المحادثات.

🍽️ الـ API هو قائمة الطعام: تخبرك بما تستطيع طلبه وكيف تطلبه، دون أن تحتاج إلى معرفة كيف يطبخ المطبخ.

التوكن: كيف يعرف الخادم من أنت؟

  1. تسجّل الدخول بمعرّفك وكلمة المرور.
  2. يتحقق الخادم ويعيد لك توكناً: نصاً سرياً عشوائياً طويلاً.
  3. تحفظه الواجهة في المتصفح: في localStorage إن اخترتَ «تذكرني» فيبقى بعد إغلاق المتصفح، وإلا ففي sessionStorage.
  4. في كل طلب بعد ذلك تضعه في الترويسة: Authorization: Token abc123.
  5. يقرأ الخادم التوكن فيعرف من أنت.
🎫 التوكن مثل بطاقة الدخول في الشركة: تأخذها مرة واحدة من الاستقبال، ثم تفتح بها كل باب دون أن تعرّف بنفسك من جديد.

والخادم لا يحفظ التوكن نفسه، بل هاشه (SHA-256). فلو سُرقت قاعدة البيانات لما استطاع أحد الدخول بحسابات الناس (القسم 17).

كلمة المرور

لا نحفظ كلمة المرور نصاً عادياً أبداً. نحفظ هاشها بخوارزمية Argon2: نص مشوّش لا يمكن إرجاعه إلى الأصل. فلو سُرقت قاعدة البيانات لما عُرفت كلمات المرور.

✍️ أسئلة

1. ما هو الـ API؟
مجموعة روابط (أبواب) يفتحها الخادم لتطلب منها الواجهة بيانات أو تنفّذ عمليات.
2. ماذا يحدث لو نسينا وضع التوكن في الترويسة؟
لا يعرف الخادم من أنت، فيعيد 401.
3. لماذا لا نحفظ كلمة المرور نصاً عادياً؟
حتى لو سُرقت قاعدة البيانات لا تُعرف كلمات المرور؛ نحفظ هاشها فقط.

4. أين تحفظ الواجهة التوكن إن اخترتَ «تذكرني»؟

في localStorage حتى يبقى بعد إغلاق المتصفح. وبدون «تذكرني» في sessionStorage.

8قاعدة البيانات (Database)

قاعدة البيانات هي المكان الذي تُحفظ فيه البيانات حفظاً دائماً. فلو أُطفئ الخادم أو حُدّثت الصفحة، تبقى الرسائل.

🍽️ قاعدة البيانات هي الثلاجة: تبقى الأغراض فيها حتى لو أُغلق المطبخ ثم فُتح.

  • الصف (Row) ➡️: سجل واحد كامل؛ الصف 2 هو رسالة سارة «أهلاً علي».

تفتح سارة المحادثة فترى الرسائل:

🔑 المفتاح الأساسي (Primary Key)

رقم مميز لكل صف لا يتكرر أبداً، وهو في تطبيقنا العمود id.

🪪 مثل الرقم الوطني: قد يتشابه اسمان، أما الرقم فلا يتكرر.

🔗 المفتاح الأجنبي (Foreign Key)

عمود في جدول يشير إلى المفتاح الأساسي في جدول آخر، ووظيفته ربط الجداول.

جدول المستخدمين:

id 🔑username

جدول الرسائل:

sender_id = 1 معناه: «اذهب إلى جدول المستخدمين وانظر من رقمه 1» ← ali.

لماذا لا نكتب الاسم مباشرة؟ لأن علياً إن غيّر اسمه غيّرناه في مكان واحد، وتبقى كل رسائله مرتبطة به ارتباطاً صحيحاً.

أنواع العلاقات

العلاقةمعناهافي تطبيقنا

Many-to-Manyكثير ← كثيرالمستخدم في محادثات كثيرة، والمحادثة فيها أكثر من مستخدم (عبر جدول العضويات)

✍️ أسئلة

1. العمود conversation_id في جدول الرسائل ما هو؟

مفتاح أجنبي، لأنه يشير إلى id في جدول المحادثات، أي يربط الرسالة بمحادثتها.

2. العمود id في جدول الرسائل ما هو؟

مفتاح أساسي: رقم مميز لكل رسالة.
3. لماذا نخزّن sender_id بدل اسم المرسل؟
حتى إن غيّر المستخدم اسمه غيّرناه في مكان واحد ويبقى الربط صحيحاً. ولأن الرقم لا يتكرر، أما الاسم فقد يتشابه.
4. ما نوع العلاقة بين المحادثة والرسائل؟
One-to-Many: محادثة واحدة فيها رسائل كثيرة.
5. ماذا يحدث لرسائل محادثة إن حُذفت المحادثة؟
تُحذف معها، بسبب on_delete=CASCADE.

11WebSocket: لماذا تصل الرسالة فوراً؟

المشكلة في HTTP

في HTTP يجب أن تطلب الواجهة أولاً حتى تأخذ جواباً؛ فالخادم لا يستطيع أن يبدأ الكلام وحده.

فلو أرسل علي رسالة، لا تعرف سارة بها إلا إذا حدّثت الصفحة. والحل السيئ أن تسأل سارة الخادم كل ثانية «هل من جديد؟»، ويُسمّى هذا Polling، وهو هدر لأن أغلب الأجوبة «لا».

📬 HTTP مثل أن تذهب إلى صندوق البريد مرة بعد مرة لترى هل وصلت رسالة.
📞 WebSocket مثل مكالمة هاتفية مفتوحة: أي طرف يتكلم في أي وقت، والآخر يسمع فوراً.

ما هو WebSocket؟

اتصال يبقى مفتوحاً بين المتصفح والخادم، وفي الاتجاهين. فيرسل الخادم الرسالة إلى سارة لحظة وصولها من علي، دون أن تطلبها.

HTTPWebSocket
الاتصاليُفتح ويُغلق مع كل طلبيبقى مفتوحاً
من يبدأ؟الواجهة فقطالطرفان
نستعمله في تطبيقنا لـالبيانات السابقة: القوائم، والرسائل القديمة، والتسجيل، والملفاتالأحداث الحية: رسالة جديدة، و«يكتب الآن»، و«متصل»، و«قُرئت»، ورنين المكالمة
الرابط يبدأ بـhttps://wss:// (أو ws:// دون تشفير)

في تطبيقنا اتصالان لكل مستخدم

  • /ws/presence/: الاتصال العام، مفتوح ما دام التطبيق مفتوحاً: «متصل الآن»، وتحديث قائمة المحادثات، والحالات الجديدة، ورنين المكالمات.
  • /ws/chat/5/: اتصال المحادثة المفتوحة: الرسائل، و«يكتب الآن»، وعلامات ✓✓.
wss://example.com/ws/chat/5/?token=abc123

لماذا التوكن في الرابط لا في الترويسة؟ لأن المتصفح لا يسمح بإضافة ترويسة إلى اتصال WebSocket.

والرسائل المتنقلة عبر WebSocket هي JSON أيضاً. ترسل الواجهة:

{"type": "message", "content": "hello"}

ويرسل الخادم إلى كل من في المحادثة:

{"type": "message", "message": {"id": 7, "content": "hello", ...}}

وأحداث أخرى:

{"type": "typing", "user_id": 1}
{"type": "presence", "user_id": 1, "is_online": true}
{"type": "read", "reader_id": 2, "message_id": 7}
«استعملتُ WebSocket لأن المحادثة تحتاج أن يرسل الخادم الرسالة إلى الطرف الآخر لحظة وصولها. في HTTP يجب أن يسأل الطرف الآخر كل حين (Polling) وهذا هدر، أما WebSocket فاتصال مفتوح في الاتجاهين.»

✍️ أسئلة

1. لماذا لا نكتفي بـ HTTP في المحادثة؟
لأن الخادم في HTTP لا يرسل شيئاً إلا إذا طلبت الواجهة، فلا تعرف سارة بالرسالة الجديدة إلا بتحديث الصفحة أو بالـ Polling.
2. ما هو الـ Polling ولماذا هو سيئ؟
أن تسأل الواجهة الخادم مرة بعد مرة «هل من جديد؟». سيئ لأن أغلب الطلبات جوابها «لا»، فهو هدر للخادم والإنترنت والبطارية.

3. عرض الرسائل القديمة حين تفتح محادثة يتم بـ؟

البيانات السابقة بـ HTTP GET، والـ WebSocket للأحداث الجديدة الحية.

4. «سارة تكتب الآن...» تصل إلى علي بـ؟

حدث حي لحظي = WebSocket.
5. لماذا نضع التوكن في الرابط مع WebSocket؟
لأن المتصفح لا يسمح بإضافة ترويسة إلى اتصال WebSocket.

12Channels: كيف تصل الرسالة إلى الشخص الصحيح؟

Django Channels هي المكتبة التي تجعل Django يفهم WebSocket، وفيها ثلاث أفكار مهمة:

1. الـ Consumer

مثل الـ View لكن لـ WebSocket. الـ View يستقبل طلباً واحداً ويعيد رداً وينتهي، أما الـ Consumer فيبقى يعمل ما دام الاتصال مفتوحاً، وفيه ثلاث دوال:

  • connect(): حين يفتح أحدٌ اتصالاً، فنتحقق من التوكن ومن أنه عضو في المحادثة.
  • receive_json(): حين تصل رسالة، فنتحقق من حدّ الإرسال، ثم نحفظها ونبثّها.
  • disconnect(): حين يُغلق الاتصال.

2. الـ Group (الغرفة)

مجموعة اتصالات نرسل إليها كلها مرة واحدة. كل من يفتح المحادثة 5 ينضم إلى الغرفة chat_5؛ فإذا أرسل علي رسالة بثثناها في الغرفة فوصلت إلى سارة.

🏠 الغرفة مثل مجموعة واتساب: ترسل إليها مرة واحدة فتصل إلى كل الأعضاء.

وفي تطبيقنا نوعان من الغرف:

الغرفةمن فيهاما يُبث فيها
chat_5كل من يفتح المحادثة 5 الآنالرسائل، و«يكتب الآن»، و«قُرئت»
user_2سارة وحدها (على كل أجهزتها)«وصلتك رسالة» لتتحدث قائمتها حتى لو لم تكن المحادثة مفتوحة، و«فلان متصل الآن» لمن يعرفها فقط، ورنين المكالمات

📌 «فلان متصل الآن» لا يُبث لكل الجامعة، بل لمن يعرفه فقط: جهات اتصاله ومن يشاركه محادثة. ولو بُثّ للجميع لكان ألفا متصل × ألفين = أربعة ملايين رسالة (القسم 16).

3. الـ Channel Layer (البريد)

النظام الذي ينقل الرسائل بين الاتصالات والغرف. في التطوير InMemory (في ذاكرة الخادم، ويكفي لعامل واحد)، وفي التشغيل الفعلي مع عدة عمّال Redis.

الرحلة الكاملة لرسالة عبر WebSocket

«استعملتُ Django Channels. لكل محادثة غرفة، وحين تصل رسالة يحفظها الـ Consumer ويبثّها في الغرفة فتصل إلى كل الأعضاء. والـ Channel Layer في التطوير InMemory، وفي التشغيل الفعلي Redis يربط العمّال.»

✍️ أسئلة

1. ما الفرق بين الـ View والـ Consumer؟
الـ View يستقبل طلباً واحداً ويعيد رداً وينتهي (HTTP). والـ Consumer يبقى يعمل ما دام اتصال WebSocket مفتوحاً، ويستقبل ويرسل في أي وقت.
2. ما هي الغرفة (Group)؟
مجموعة اتصالات نرسل إليها مرة واحدة فتصل إلى الجميع، مثل مجموعة واتساب.

3. إن صار عندنا عدة عمّال (خوادم)، ماذا نغيّر؟

InMemory يعيش في ذاكرة عامل واحد، ومع عدة عمّال نحتاج Redis ليتشاركوا. ونستعمل PostgreSQL لقاعدة البيانات.
4. لماذا أنشأنا غرفة user_2 لسارة؟
لتصلها تنبيهات الرسائل الجديدة حتى لو لم تكن المحادثة مفتوحة، فتتحدث قائمة المحادثات وعدد غير المقروء دون تحديث الصفحة، ولتصلها المكالمات.
5. في أي دالة من الـ Consumer نتحقق من التوكن؟
في connect().

🚪 ما هو Daphne؟

كود Django الذي كتبناه (الـ views والـ models) لا يعرف استقبال الطلبات من الشبكة وحده؛ يعرف فقط «إذا وصلني طلب فماذا أفعل». فنحتاج برنامجاً يقف على الباب (المنفذ)، يستقبل الطلبات، ويسلّمها إلى Django، ويعيد الجواب. هذا يُسمّى خادم التشغيل (Server)، وDaphne واحد منها.

🍽️ Django هو الطبّاخ: يعرف الطبخ لكنه لا يقف على الباب. وDaphne هو النادل على الباب: يستقبل الطلبات ويوصلها إلى الطبّاخ ويعيد الأطباق. والمنفذ 8000 هو رقم باب المطعم.

لماذا Daphne بالذات؟

النوعيدعمأمثلة
WSGI (القديم)HTTP فقطGunicorn
ASGI (الحديث)HTTP وWebSocketDaphne، وUvicorn

تطبيقنا يحتاج WebSocket، فلا بد من خادم ASGI. وDaphne صنعه فريق Django Channels نفسه.

📌 ولأن 'daphne' هو أول عنصر في INSTALLED_APPS داخل settings.py، فإن الأمر العادي python manage.py runserver يشغّل Daphne تلقائياً، وهذا ما يستعمله run-mobile.sh.

📌 وفي التشغيل الفعلي (Docker) نفصل العملين: Gunicorn للطلبات العادية (/api)، وUvicorn لاتصالات WebSocket، وكلاهما بعدة عمّال (القسم 16).

❓ هل Daphne هو الـ API؟ لا!

  • الـ API هو قائمة الطعام: الروابط التي يقبلها تطبيقنا وما يفعله كل منها. نحن كتبناه: الروابط في urls.py، والمنطق في views.py.
  • Daphne هو النادل: يوصل أي طلب إلى كودنا، ولا يعرف معنى /api/conversations/، بل يوصله فقط.

Browser → Daphne (port 8000) → config/asgi.py → urls.py → views.py → Database → views.py → Daphne → Browser

🍽️ النادل نفسه قد يعمل في مطعمين، لكن لكل مطعم قائمة طعام مختلفة.
«الـ API هو الروابط التي عرّفتُها في urls.py ومنطقها في views.py. وDaphne خادم ASGI يستقبل طلبات HTTP وWebSocket على المنفذ ويسلّمها إلى Django. استعملته لأن تطبيقي يحتاج WebSocket عبر Django Channels، وفي التشغيل الفعلي أستعمل Gunicorn للـ API وUvicorn للـ WebSocket.»

ما تعلمناه: التخمين الأول كان خاطئاً، والمعلومات (sudo ss وdocker ps) هي التي كشفت الحقيقة. (ولهذا صار run-mobile.sh يكشف بنفسه من يحجز المنفذ.)

🐳 ما هو Docker؟

Docker برنامج يشغّل التطبيقات داخل صناديق مغلقة (Containers)، في كل صندوق تطبيق كامل مع كل ما يحتاجه (Python، والمكتبات، والإعدادات). ويستطيع الصندوق ربط باب من داخله بباب في جهازك؛ فالعبارة 0.0.0.0:8000->8000/tcp معناها: أي طلب يصل إلى الباب 8000 في جهازك يذهب إلى الباب 8000 داخل الصندوق.

📦 Docker مثل شقق مفروشة جاهزة: تسكنها فوراً دون شراء أثاث. لكن إن نسيتَ شقة مسكونة بقيت تشغل رقمها في العمارة!
الأمرما يفعله

docker stop <name>يوقف صندوقاً (ولا يحذفه)
docker start <name>يعيد تشغيله

ونستعمل Docker نفسه لتشغيل «وَصل» على خادم حقيقي بسبع خدمات؛ تفاصيلها في القسم 27.

🌐 ما هو CORS؟

CORS قاعدة أمان في المتصفح: لا يستطيع موقع أن يطلب من خادم آخر إلا إذا وافق الخادم. فالخادم لديه قائمة بالمواقع المسموح لها.

وقبل الطلب الحقيقي يرسل المتصفح طلب استئذان اسمه preflight (نوعه OPTIONS)؛ فإن لم يردّ الخادم بـ «مسموح» (الترويسة Access-Control-Allow-Origin) أوقف المتصفح الطلب وظهر «Failed to fetch».

🍽️ المطعم يستقبل الطلبات من صالته فقط؛ فإن جاء طلب من صالة أخرى رفضه النادل. وCORS يحمي المستخدم: لا يستطيع موقع غريب استعمال حسابك في موقع آخر.
«CORS قاعدة أمان في المتصفح: يجب أن يوافق الخادم على الموقع الذي يطلب منه. في التطوير سمحتُ لأي منفذ على جهازي، وفي التشغيل الفعلي الواجهة والخادم على العنوان نفسه خلف البوابة.»

🧠 كيف يفكر المبرمج (أهم درس)

  1. انظر إلى الخطأ: مثل «Failed to fetch»؛ وهو وحده لا يذكر السبب.
  2. اجمع معلومات أكثر: الـ Console (F12)، والطرفية، وأوامر الفحص.
  3. افهم السبب: مثلاً «الباب خطأ» أو «البرنامج القديم ما زال يعمل».
  4. أصلح شيئاً واحداً فقط، ثم جرّب مرة أخرى.

📌 القاعدة الذهبية: لا تخمّن؛ اجمع المعلومات أولاً. واكتب الأوامر سطراً سطراً لتعرف أيها فشل.

  • Pillow مكتبة تفتح الصورة لتتأكد أنها صورة حقيقية لا ملف آخر متنكر.

«الصور تُرسل بـ multipart/form-data، وDjango يحفظ الملف في MEDIA_ROOT وقاعدة البيانات تحفظ مساره فقط، وأتحقق أنها صورة حقيقية بمكتبة Pillow مع حد للحجم.»

3. إعادة الاتصال (Reconnect)

اتصال WebSocket مفتوح، لكنه قد ينقطع: ينقطع الإنترنت، أو ينام الهاتف، أو يُعاد تشغيل الخادم. وحينها:

  1. يظهر في الترويسة «جارٍ الاتصال...».
  2. يحاول الاتصال من جديد بعد ثانية، ثم 2، ثم 4، ثم 8... حتى 30 ثانية. وهذا اسمه Exponential Backoff: لا نضغط على الخادم بآلاف المحاولات دفعة واحدة.
  3. وحين يعود يجلب الرسائل بـ HTTP حتى لا يفوته شيء حدث أثناء الانقطاع.
  4. وإن أرسلتَ رسالة والاتصال مقطوع، تُرسل بـ HTTP POST بدل WebSocket.

الملف: frontend/lib/socket.ts.

5. PWA: تطبيق على الشاشة الرئيسية

PWA (Progressive Web App) موقع يتصرف كتطبيق: يُضاف إلى الشاشة الرئيسية بأيقونة، ويُفتح دون شريط المتصفح، ويستقبل الإشعارات. ويحتاج أمرين:

📱 الـ Manifest هوية التطبيق، والـ Service Worker حارس يبقى مستيقظاً في الخلفية ويستقبل الإشعارات وأنت نائم.

6. إشعارات Push: الرحلة الكاملة

الإشعار لا يصل من خادمنا إلى الهاتف مباشرة، بل يمر عبر خدمة الإشعارات التابعة لشركة المتصفح (Google لـ Chrome، وApple لـ Safari، وMozilla لـ Firefox).

أولاً: الاشتراك (مرة واحدة، حين تضغط «تفعيل»):

  1. يطلب المتصفح إذنك.
  2. يأخذ المفتاح العام لخادمنا من GET /api/push/key/.
  3. يذهب إلى شركته فينشئ «عنواناً» خاصاً بجهازك (endpoint).
  4. نرسل العنوان إلى الخادم بـ POST /api/push/subscribe/ ونحفظه في جدول PushSubscription.

ثانياً: الإرسال (مع كل رسالة جديدة):

Ali sends → create_message() → pywebpush → Google/Apple push service → Sara's Service Worker → notification 🔔
  • يتم الإرسال في طابور خلفي (8 عمّال ثابتين) حتى لا تتأخر الرسالة بانتظار Google أو Apple.
  • إن قالت الشركة إن العنوان «ميت» (404 أو 410) حذفناه.
  • يصل الإشعار بلغة المستلم، ويمكن إخفاء نصه لمن طلب ذلك.
  • إن كانت سارة تشاهد المحادثة نفسها لا يظهر إشعار، إلا على أجهزة Apple: فهي تشترط عرض إشعار مع كل Push، وإلا ألغت الاشتراك.
  • الضغط على الإشعار يفتح المحادثة نفسها (/chat?c=5).

🔑 ما هو VAPID؟

زوج مفاتيح هو هوية خادمنا عند خدمات الإشعارات:

  • المفتاح العام: يُعطى للمتصفح وقت الاشتراك.
  • المفتاح الخاص: يبقى سرياً عندنا (الملف backend/vapid_keys.json ولا يُرفع إلى GitHub)، ونوقّع به كل إشعار، فلا يستطيع غيرنا إرسال إشعارات باسم تطبيقنا.
  • ومعه VAPID_CONTACT: عنوان تواصل حقيقي. وحين كان وهمياً رفضت Apple الإشعارات فلم تصل إلى الآيفون، ثم أصلحناه.
✍️ مثل التوقيع والختم: خدمة الإشعارات ترى التوقيع فتتأكد أن الإشعار من خادمنا فعلاً.
«الإشعارات بتقنية Web Push: يشترك المتصفح لدى خدمة إشعارات شركته، وأحفظ الاشتراك في قاعدة البيانات. ومع كل رسالة يوقّع الخادم الإشعار بمفتاح VAPID ويرسله إلى خدمة الإشعارات، فتوصله إلى الـ Service Worker ولو كان التطبيق مغلقاً.»

طبقات الحماية عندنا

  1. HTTPS: الطريق بين الهاتف والخادم مشفّر، فلا يقرأ أحد في الشبكة شيئاً.
  2. كلمات المرور بـ Argon2: بطيئة عمداً وتحتاج ذاكرة، فتخمين ملايين الكلمات مكلف جداً.
  3. التوكنات بالهاش: نحفظ SHA-256 للتوكن فقط، فلو سُرقت قاعدة البيانات لما سُرق دخول أحد. وتسجيل الخروج يحذف التوكن.
  4. الرسائل مشفّرة في قاعدة البيانات: العمود content فيه enc1:… لا النص، ونفك التشفير عند القراءة فقط.
  5. الملفات مشفّرة على القرص: قطع كل منها 64 كيلوبايت مشفّرة، فيعمل الفيديو ويتقدم (Range) دون فك الملف كله.
  6. روابط الملفات موقّعة ومؤقتة (HMAC): دون التوقيع الصحيح يعود 403، وتنتهي بعد ساعات.

الملفات: backend/config/settings.py (Argon2)، وbackend/accounts/tokens.py (التوكن)، وbackend/chat/crypto.py وfields.py (التشفير)، وbackend/config/media.py (الروابط الموقّعة).

لماذا ليس تشفيراً طرفاً لطرف (E2EE) مثل واتساب؟

في E2EE لا يستطيع حتى الخادم القراءة. وهو قوي، لكنه يعطّل أشياء نحتاجها الآن: نص الرسالة في الإشعار، وفتح الحساب من أكثر من جهاز (كل جهاز يحتاج مفاتيحه). فاخترنا التشفير في الخادم الآن، وE2EE مرحلة لاحقة.

⚠️ المفتاح أهم شيء: إن ضاع مفتاح الرسائل (backend/message_key) لا تُقرأ أبداً، فيجب نسخه احتياطياً في مكان آمن.

«كلمات المرور بـ Argon2، والتوكنات أحفظ هاشها فقط. والرسائل والملفات مشفّرة بـ AES-256-GCM في قاعدة البيانات والقرص، وروابط الملفات موقّعة بـ HMAC ومؤقتة، والنقل كله HTTPS. وE2EE خطوة لاحقة لأنها تؤثر في الإشعارات وتعدد الأجهزة.»

✍️ أسئلة

1. هل نشفّر كلمات المرور أم نصنع لها هاشاً؟

حتى نحن لا نعرف كلمة مرور أحد.

2. لماذا نحفظ هاش التوكن لا التوكن نفسه؟

الفكرة نفسها في كلمة المرور.
3. ماذا يحدث إن عرف أحدٌ مسار ملف رسالة دون التوقيع؟
يعود له 403. والملف نفسه مشفّر على القرص، فحتى لو وصل إلى القرص لا يقرأ شيئاً دون المفتاح.
4. ما الفرق بين التشفير في الخادم وE2EE؟
في الخادم: الرسالة مشفّرة في التخزين لكن الخادم يملك المفتاح. في E2EE: المفتاح في جهازَي الطرفين فقط، والخادم لا يستطيع القراءة ولو أراد.

لماذا يلزم https؟

Mobile → https://xxx.trycloudflare.com → cloudflared → Next.js (3000) → /api و /ws → Django (8000)

فالواجهة (Next.js) تمرر طلبات /api و/ws و/media إلى Django (الإعداد في frontend/next.config.ts)، فيكفي رابط واحد. وفي Docker تتولى البوابة Caddy هذا العمل.

21.4كيف تفرّق TypeScript عن JavaScript؟

هما متشابهتان جداً، لأن TypeScript هي JavaScript مع «الأنواع». أربع علامات تكفي:

  1. الامتداد: .ts أو .tsx تعني TypeScript، و.js أو .jsx تعني JavaScript.
  2. الأنواع بعد النقطتين: name: string، id: number، user: User. هذه غير موجودة في JavaScript.
  3. تعريف الأنواع بكلمتَي type أو interface. مثال من frontend/lib/api.ts: export type User = { id: number; username: string; ... }.
  4. وجود الملف frontend/tsconfig.json، وهو إعدادات TypeScript، وكلمة "typescript" داخل frontend/package.json.

29أسئلة المدير المتوقعة وأجوبتها

29.1 ما لغة المشروع؟

الخادم Python بإطار Django، والواجهة TypeScript بإطار Next.js مع React (القسم 23).

29.2 أين ملف الإعدادات؟ وماذا فيه؟

backend/config/settings.py: فيه الأمان (SECRET_KEY وDEBUG)، والتطبيقات المفعّلة، وقاعدة البيانات، وهاش كلمات المرور (Argon2)، واللغة، وRedis، وإعدادات الـ API وحدود الطلبات، وأماكن الملفات، والإشعارات، والمكالمات (القسم 24). والأسرار تأتي من ملف .env لا من الكود.

29.3 أين الـ API؟

الروابط في backend/*/urls.py، ومنطقها في backend/*/views.py، وأكبرها backend/chat/views.py. وفي الواجهة تُستدعى من frontend/lib/endpoints.ts.

29.4 أين قاعدة البيانات والجداول؟

تعريف الجداول في backend/*/models.py. في التطوير ملف backend/db.sqlite3، وفي التشغيل الفعلي PostgreSQL داخل Docker.

29.5 أين الهاش والتشفير؟

هاش كلمات المرور: PASSWORD_HASHERS في settings.py (Argon2). هاش التوكن: backend/accounts/tokens.py. تشفير الرسائل والملفات: backend/chat/crypto.py وfields.py.

29.6 أين الرسائل الفورية (WebSocket)؟

الخادم: backend/chat/consumers.py وrouting.py. الواجهة: frontend/lib/socket.ts.

29.7 أين الشاشات؟

في frontend/app/chat/_ui/، وكل شاشة في ملف باسمها (القسم 26.3)، وبوابة الدخول في frontend/app/AuthForm.tsx.

29.8 كيف تشغّل المشروع؟

على الحاسوب: ./run-mobile.sh. على خادم حقيقي: cd deploy && ./start.sh (Docker). والاختبارات: cd backend && python manage.py test.

29.9 ما الفرق بين views.py وurls.py وmodels.py؟

models.py يعرّف الجداول (ماذا نحفظ)، وviews.py يقرر ماذا يحدث عند كل طلب (المنطق)، وurls.py يربط كل رابط بدالته في views.py. مثال: الرابط /api/conversations/ في urls.py يذهب إلى الدالة conversations في views.py، التي تقرأ من جدول Conversation المعرّف في models.py.
